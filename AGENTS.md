# AGENTS.md: Operating Manual for AI Implementers

You are implementing **Praxis**. This file is binding. Read it fully before writing code.

## 0. Prime directives
1. **The spec is the source of truth.** `spec/` is normative; `docs/` explains intent. If code and spec disagree, the spec wins, or you open an ADR/PIP to change it. Never silently diverge.
2. **Do not invent cryptography.** Use only the primitives/libraries named in `docs/TECH_STACK.md`. No custom ciphers, KDFs, signature schemes, or RNG. If you think you need one, stop and open an issue labelled `needs-human-crypto-review`.
3. **No telemetry, no network calls by default.** The core and CLI must function fully offline. Any outbound request must be explicit, user-initiated, and documented.
4. **Privacy by construction.** Never log plaintext case bodies, keys, or elicitation answers. Logs may contain object IDs (CIDs) and error codes only.
5. **Determinism.** All signed/hashed data uses deterministic encoding (spec/PROTOCOL.md §3). No floats in signed objects. Never use wall-clock time inside canonicalization.
6. **Smallest correct step.** Implement the current milestone only. Do not build "future" features. Mark unresolved design questions with `// OPEN(Q-xxx)` and add to `docs/EVALUATION.md` open-questions list.
7. **Honesty over polish.** If a requirement is infeasible or a test fails, say so in the PR; never weaken tests to pass.

## 1. Reading order
`README.md` → `docs/VISION.md` → `docs/PRODUCT_SPEC.md` → `docs/ARCHITECTURE.md` → `docs/TECH_STACK.md` → `spec/PROTOCOL.md` → `spec/praxis-v0.1.cddl` → `spec/SCORING.md` → `docs/IMPLEMENTATION_PLAN.md` (find your current milestone) → the docs for the component you're touching.

## 2. Workflow
- Work from `docs/IMPLEMENTATION_PLAN.md` in order. Each task has an ID (e.g. `M1-03`) and **acceptance criteria**. A task is done only when *all* criteria pass in CI.
- One task per PR. Branch: `m1-03-canonical-cbor`. Commit style: Conventional Commits (`feat(types): ...`). Sign off commits (DCO: `git commit -s`).
- Every PR must: add/modify tests, update docs if behavior changed, pass `just ci` (fmt, clippy `-D warnings`, tests, `cargo deny`, `cargo audit`, docs build), and fill the PR template.
- Spec changes: open a **PIP** (Praxis Improvement Proposal) in `spec/pips/` (see GOVERNANCE.md). Architectural changes: add an **ADR** in `adr/`.
- If blocked >1 attempt on the same failure, stop, write up what you tried, and open an issue rather than thrashing.

## 3. Definition of Done (global)
- [ ] Acceptance criteria in plan met
- [ ] Unit + property tests (use `proptest` for codecs/scoring) + golden test vectors where the spec defines them
- [ ] No `unsafe` in non-FFI crates (`#![forbid(unsafe_code)]`); FFI crates isolate and document each `unsafe`
- [ ] Public API documented (`#![deny(missing_docs)]`)
- [ ] Errors are typed (`thiserror`), never `unwrap()`/`expect()` outside tests
- [ ] Docs updated; CHANGELOG entry
- [ ] Threat-model impact noted if the change touches keys, sealing, sync, or policy

## 4. Test strategy requirements
- **Cross-implementation vectors:** `spec/test-vectors/` is generated by the Rust reference implementation *and independently verified* by a second implementation (TypeScript, in `sdk/ts`) before M1 closes. Divergence = spec bug or impl bug; resolve before proceeding.
- **Property tests:** encode∘decode = identity; ID stability under map-key reordering of input; signature verification fails on any single-bit flip.
- **Scoring:** golden numerical tests against hand-computed examples in `spec/SCORING.md`; fuzz tests for degenerate inputs (all-same outcomes, n=0, p∈{0,1}).
- **Fuzzing:** `cargo-fuzz` targets for every parser (CBOR decode, sealed-body parse, sync messages).
- **Security regression tests:** each fixed vuln gets a test named `sec_<id>_*`.

## 5. Style & structure
- Rust stable, edition 2021 (bump per `rust-toolchain.toml`). `rustfmt` + `clippy::pedantic` (allow-list justified in code).
- TypeScript: strict mode, ESM, no `any`. Python: 3.12+, `ruff` + `mypy --strict`, managed with `uv`.
- Public identifiers use the glossary terms exactly (`Case`, `Event`, `Claim`, `Canon`...). Don't coin synonyms.
- Keep crates small and acyclic per `docs/ARCHITECTURE.md` §3 dependency rules.

## 6. Things you must NOT do
- Do not add analytics, crash reporting, auto-update pings, or "phone home".
- Do not add features that rank, score, or report on people *to third parties* without the practitioner's explicit per-disclosure consent (ETHICS.md §2). Calibration is a **practitioner-controlled disclosure**, not an employer dashboard.
- Do not store secrets in the repo, tests, or fixtures. Test keys are generated at test time or are clearly labelled `TEST_ONLY_` constants.
- Do not copy code from incompatible licenses. Note provenance of any adapted snippet.
- Do not claim the central hypothesis is proven. Say "supported by pre-registered study X" only when it is.

## 7. When in doubt
Prefer: **simpler > clever**, **explicit > implicit**, **boring > novel**, **spec'd > assumed**, **ask > guess**.
